# AGENTS.md - developing the Ozone CLI

Development guide for this module (`cli/`, artifact `com.ozonehis:cli`,
command `ozone`). Written for human developers and equally usable by AI
coding agents - follow it when changing or extending the CLI. Read `README.md`
first for the user-facing behavior.

## Naming rules (strict)

- The user-facing command is `ozone`. In comments, strings, docs and commit
  messages, refer to the tool as **the Ozone CLI** - never bare "ozone" when it
  means the tool.
  Command invocations in prose are quoted: `'ozone resolve'`.
- Maven artifact `com.ozonehis:cli`; Java package `com.ozonehis.cli`; main
  class `com.ozonehis.cli.OzoneCli`. The distro's config folder is `meta/`.
- Generated-file headers: `# Generated by the Ozone CLI …` for `.env` and
  `manifest.yml`; `# Generated by 'ozone resolve' - do not edit. Regenerate
  with: 'ozone resolve'` for `resolved/*`. Test fixtures must mirror these
  headers exactly.

## Architecture

`OzoneCli` parses args and orchestrates. The rest is small, single-purpose
classes in `com.ozonehis.cli`:

- `Model` - parses the compose project's `configs/model.yml`; `mergeOverlay`
  applies the distro's `model-overrides.yml` (additive only).
- `Selection` - parses `meta/selection.yml` (apps list + modes map).
- `Resolver` - computes the compose-file chain and profiles from model +
  selection + resolved overlay.
- `Plan` - the resolved deployment plan (apps, modes, chain, restore command).
- `EnvGen` - builds the `.env`. Merge order (later wins): code-level
  `configs/vars.yml` → distro `resolved/vars.yml` → the model's
  `deployment:` section. The `.env` is portable: `HOST_NAME`/`DISTRO_PATH`
  are never stored in it.
- `DistroMerge` - the `resolve` command: merges parent `resolved/` with own
  `meta/` sources into `meta/resolved/` (`MERGED_FILES = {vars.yml,
  model-overrides.yml}`) and records `info.yml` from `--project-*`.
- `YamlMerge` / `Yamls` - YAML merge and load/dump helpers.
- `ComposePaths` - resolves compose file paths by declaration: base-model
  files against the compose root, overlay-declared files against the distro
  dir. An overlay naming a base-model file is a loud error.
- `Display` - all console output. Glyphs have fixed meanings: ✓ confirmation,
  ● a row, 🔑 credentials, ℹ note. Rules/notes align to `RULE_WIDTH = 72`. The
  printed compose command is fenced between rules and must stay byte-exact
  (multi-line, one continuation line per prefix assignment - this format is
  intentional; do not "tidy" it).

## Core principles

- **No magic.** Declarations decide; never probe the file system, guess, or
  parse strings to infer intent. Anything ambiguous → fail loudly. Errors are
  `IOException`s prefixed `ozone: ` with an actionable message (often citing
  the command to run, e.g. `ozone resolve --to <distro-dir>`).
- Booleans: anything other than `true` (incl. `false`, empty) is false.
- Nothing is generated in source trees. `meta/resolved/`, `meta/.env`,
  `meta/manifest.yml` exist only in built artifacts / at deployment
  (gitignored at the repo root: `distro/meta/{resolved/,.env,manifest.yml}`).
- Merge semantics (YamlMerge): maps recurse, lists append, scalars
  child-wins, type conflicts = loud error. `selection.yml` is NOT merged -
  it replaces the parent's wholesale via the build-time file copy.

## Maven wiring (in the main Ozone repo - do not duplicate by hand)

- `maven-parent/pom.xml`: property `cli.version`; `meta` profile (activated by
  `${basedir}/meta`) with the `com.ozonehis:cli` dependency, "Copy local
  meta/ resources" (process-resources; excludes `resolved/**`, `.env`,
  `manifest.yml`) and "Resolve meta sources" (prepare-package; `exec:java`
  `com.ozonehis.cli.OzoneCli` with `resolve --from
  ${project.build.directory}/${ozone.artifactId}/distro --to
  ${project.build.directory}/${project.artifactId}-${project.version}/distro
  --project-name ${project.artifactId} --project-version ${project.version}
  --project-description ${project.description}`). The cli jar is excluded from
  "Copy OpenMRS modules to a temporary location" (`excludeArtifactIds cli`).
- `distro/pom.xml` (root distro): same two executions, without `--from`, plus
  the `com.ozonehis:cli:${project.version}` dependency.
- `info.yml`'s name/version/description come from the child's own Maven
  attributes; a child pom must declare its own `<description>` (otherwise
  Maven inherits the parent's - there is no way to detect that, by design).

## Build, test, smoke

The `ozone` launcher and its PATH helpers live in this module at `cli/bin/`
(`ozone`, `ozone-path.sh` for sh/bash/zsh, `ozone-path.fish` for fish); the
root build copies them into the artifact as `bin/*` next to `bin/cli.jar`
(the CLI jar), so a built Ozone zip runs `bin/ozone ...` directly. The
session-local dev shims `ozone-local.sh` / `ozone-local.fish` (define an
`ozone` shell function over `cli/target/cli-*.jar`) are excluded from the
artifact; source them from the repo root to use the CLI built from source.

```
cd cli && mvn clean package
java -jar target/cli-1.0.0-SNAPSHOT.jar \
  --compose-root src/test/resources/fixture/compose \
  --distro src/test/resources/fixture/distro --hostname demo.local validate
```

Fixtures live in `src/test/resources/fixture/{compose,distro}`; tests in
`src/test/java/com/ozonehis/cli/` (`DistroMergeTest`, `ResolverTest`,
`EnvGenTest`, …). When changing USAGE text, keep the command column aligned.
When changing generated headers, update the fixtures in the same commit.
