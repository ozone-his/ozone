# Ozone CLI

The Ozone CLI (command `ozone`, Maven artifact `com.ozonehis:cli`) assembles the
Docker Compose command of an Ozone distribution from the compose project's
**model** and the distro's **selection**. It prints commands; it never runs
them. It also resolves the distro build's inheritance chain at build time.

## Why it exists

Ozone (the product) is one compose project, but it is deployed as many
distributions, on many machines, by different actors. Configuration is
therefore specified at distinct moments and places, each with its own owner:

#### Code level - owned by the Ozone product

What *can* run at all: the apps, integrations, support services, modes and
the rules of how they combine, plus the default values of every variable.
This is shipped inside every artifact.

#### Distro level - authored by each distribution

What *this* distro runs and how it differs from its parent: which apps and
modes are enabled, its variable overrides, and any compose additions of its
own.

#### Build time - per distro, via Maven

The inheritance chain of a multi-level distro is flattened once, at build
time, and the distro's identity (name, version, description) is recorded. The
published artifact is therefore self-contained and ready to deploy.

#### Deployment time - per machine

The final environment, derived from the resolved chain and the selection.

#### Invocation - per run

The machine/deployment specific values (hostname, distro location), provided
with the invocation itself rather than stored, so generated files stay
portable across machines.

#### Run time

The services themselves, started by `docker compose`.

### --- 

This split is what makes the problem complex: the same deployment is described
by layers owned by different people at different times, and no single file can
answer "what will actually run here". The root requirements are:

- **Enable/disable apps, support services and modes without touching compose
  files**: a distro only declares its selection; the CLI computes the exact
  compose file chain and profiles. Removing a service means omitting it from
  the selection, not editing compose files.
- **Flexible environment variable manipulation across all levels**: defaults
  from the product, overlaid by each distro level (parent to child, with
  explicit merge rules), plus deployment-time knobs and invocation-time values.
- **Multi-level distros**: root distro -> child -> grandchild. Because Maven
  knows the full dependency chain, the inheritance is resolved at build time;
  deployment then needs no Maven context, only the published artifact.

The Ozone CLI exists to be the single, explicit tool at the center of this: it
resolves the distro chain at build time and assembles the exact compose command
at deployment time - printing it, never running it.

## The distro's `meta/` directory

Everything the CLI reads and writes lives in the distro's `meta/` dir:

| File | Authored or generated | Role |
|---|---|---|
| `meta/selection.yml` | authored | Which apps and modes are on. Replaces the parent's selection wholesale (build-time file overlay) - disabling a service is done here |
| `meta/vars.yml` | authored | This distro's variable values. Merged over the parent's `resolved/vars.yml` (see merge rules) and laid over the compose project's `configs/vars.yml` |
| `meta/model-overrides.yml` | authored | Compose fragments this distro adds on top of the base model. Merged additively over the parent's `resolved/model-overrides.yml`. Never removes entries |
| `meta/resolved/vars.yml` | generated by `ozone resolve` at build | Flattened vars chain - the only vars source read at deployment |
| `meta/resolved/model-overrides.yml` | generated by `ozone resolve` at build | Flattened model overlay chain - the only model overlay source read at deployment |
| `meta/resolved/info.yml` | generated by `ozone resolve` at build | Distro identity: `name` (the compose project name, from the build's `--project-name`, i.e. the artifactId), `version`, `description` |
| `meta/.env` | generated at deployment | The env file for `docker compose --env-file`. Portable: it never stores `HOST_NAME` or `DISTRO_PATH` - the printed command provides them |
| `meta/manifest.yml` | generated at deployment | Echoes `info.yml` and lists the compose files of the selection |

`resolved/`, `.env` and `manifest.yml` are generated - never edited by hand,
never committed (gitignored).

## The compose project

The compose root (in a built Ozone artifact: the unpacked `run/docker` dir)
carries the code-level defaults:

- `configs/model.yml` - the base model: everything that *can* run (apps,
  integrations, modes, database services, incompatibilities) and the rules of
  combination. Compose file paths in the base model are relative to the compose
  root.
- `configs/vars.yml` - code-level variable defaults.

## Merge rules (`ozone resolve`)

Merging the parent's `resolved/` files with this distro's own sources:

- maps merge recursively,
- lists are appended,
- scalars: the child's value wins,
- type conflicts (map vs list vs scalar): loud error, the build fails.

Paths in `vars.yml` `paths:` values and in `model-overrides.yml` compose file
lists are relative to the **distro dir**; an overlay may not declare a file
that belongs to the base model (loud error).

## Usage

In a built Ozone artifact the CLI is bundled as `bin/ozone` (a launcher for
the shipped `bin/cli.jar`). To use the bare `ozone` command, either source the
helper or export PATH yourself:

```
. ./bin/ozone-path.sh        # sh/bash/zsh; in fish: source ./bin/ozone-path.fish
                             # or simply: export PATH="$PWD/bin:$PATH"
ozone --compose-root ...    # then use 'ozone' directly
```

Elsewhere, run the jar directly: `java -jar cli-<version>.jar ...`.

### From the source tree (development)

Build the CLI and source the session-local shim - no artifact needed:

```
mvn -pl cli package
. cli/bin/ozone-local.sh        # sh/bash/zsh; in fish: source cli/bin/ozone-local.fish
ozone --compose-root ...        # uses cli/target/cli-*.jar, this session only
```

```
ozone resolve [--from <parent-distro-dir>] --to <distro-dir>
              [--project-name <n>] [--project-version <v>] [--project-description <d>]

ozone --compose-root <dir> --distro <dir> [--hostname <h>]
      [--scheme <http|https>] [--env-file <path>] [--manifest <path>]
      [--no-credentials] <run | up [mode] | down | restore | validate | manifest>
```

- `resolve` (build time): merge the parent distro's `resolved/` files with this
  distro's own `meta/` sources into `meta/resolved/`, and record the
  `--project-*` identity as `resolved/info.yml`.
- `run` prints the `docker compose ... up -d` command for the selection; `up
  [mode]` additionally prints the ad-hoc chain of that mode (e.g. `up backup`).
  `down`, `restore`, `validate`, `manifest` do what they say; `manifest`
  (also run by `run`/`up`) generates `manifest.yml` and `.env` and prints the
  summary. All of these read `meta/resolved/` + `meta/selection.yml` only.
- `--compose-root` - the Docker Compose project location (required except for `resolve`).
- `--distro` - the distro location (required except for `resolve`).
- `--hostname` - required for `run`/`up`/`restore`/`down`: the deployment's
  hostname, or the machine's IP for local runs (localhost breaks SSO, e.g. on
  macOS).

The command is printed multi-line, fenced between rules, byte-exact for
copy/paste:

```
DISTRO_PATH='<distro dir>' \
 HOST_NAME=<hostname> \
 docker compose \
  --project-directory <compose root> \
  -p <project name> \
  --env-file <distro>/meta/.env \
  -f <compose file> \
  ... \
  up -d
```

## Examples

`ozone --help` prints the same examples.

Build time - resolve this distro's `meta/` sources against its parent (run by
the Maven build; run by hand only to regenerate `meta/resolved/`):

```
ozone resolve --from target/ozone/distro --to target/my-distro-1.0.0-SNAPSHOT/distro \
              --project-name my-distro --project-version 1.0.0-SNAPSHOT \
              --project-description 'My distro'
```

Deployment - from an unpacked Ozone artifact:

```
ozone --compose-root run/docker --distro distro --hostname demo.local run
ozone --compose-root run/docker --distro distro --hostname demo.local up backup
ozone --compose-root run/docker --distro distro --hostname demo.local down
```

## Build wiring (Maven)

Child distros inherit the resolve step from `maven-parent` via the `meta`
profile (activated when the project has a `meta/` dir): it copies the distro's
own `meta/` sources into the assembled artifact and runs `ozone resolve`
against the parent Ozone zip unpacked in `target/`. The root Ozone distro
(`distro/pom.xml`) runs the same step without a parent. Nothing is generated
in source trees - only in the built artifact.
